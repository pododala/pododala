# 클라우드 아키텍처와 DDD 기반 MSA 설계 개념

클라우드 이전과 애플리케이션 아키텍처 변경은 서로 다른 결정이다. 기존 시스템을 클라우드에 옮기는 것만으로 API Gateway, BFF, MSA, Saga 또는 DDD가 필수 요소가 되지는 않는다. 각 구성요소는 해결하려는 문제와 그에 따른 비용을 기준으로 선택해야 한다.

## 클라우드 서비스 모델: IaaS·PaaS·SaaS

- **IaaS(아이아스)**: 가상 서버·네트워크·스토리지 등 인프라를 제공한다. 운영체제와 애플리케이션 관리는 주로 이용자가 맡는다.
- **PaaS(파스)**: 애플리케이션 실행·배포 플랫폼을 제공한다. 개발자는 주로 코드와 데이터에 집중한다.
- **SaaS(사스)**: 완성된 소프트웨어를 서비스 형태로 제공한다.

이 분류는 자원과 운영 책임의 범위를 나타내며, BFF나 MSA 같은 애플리케이션 설계 패턴과는 별개다.

## WEB·WAS·DB와 Gateway Layer

전통적인 웹 애플리케이션은 웹 서버가 요청을 받아 WAS로 전달하고, WAS가 업무 로직과 데이터 접근을 처리하는 구조를 사용할 수 있다. 웹 서버가 리버스 프록시·라우팅·부하 분산을 수행한다면 그 **기능**을 논리적인 게이트웨이 계층으로 표현할 수 있다.

그러나 웹 서버가 존재한다는 사실만으로 독립된 **API Gateway 제품이나 서버**가 존재한다고 단정할 수 없다. API Gateway는 API 라우팅, 인증 정책, 요청 제한 등 공통 API 관리 기능을 제공할 수 있다. 기존 웹 서버와의 기능 중복 여부를 검토해야 한다.

## BFF(Backend for Frontend)

BFF는 웹·모바일 등 클라이언트 유형별 요구에 맞춰 백엔드 API를 호출하고 결과를 조합·가공하는 계층이다. 예를 들어 서로 다른 화면이 같은 업무 서비스에서 다른 필드나 응답 형태를 요구할 때 유용하다.

BFF를 도입해도 기존 백엔드 Controller는 남을 수 있으며, BFF 자체에도 요청을 받는 Controller가 생길 수 있다. 따라서 **호출 단계 추가 자체가 장점은 아니다.** 클라이언트 로직 단순화, 화면별 변경의 독립성, API 조합 책임 분리가 실제 이점이다.

BFF 도입이 자동으로 단일 장애점(SPOF)을 없애거나 전체 복잡도와 운영비용을 줄이는 것은 아니다. BFF를 단일 인스턴스로 운영하면 새로운 장애 지점이 될 수 있다. 효과를 평가할 때는 중복 개발 감소와 함께 추가 배포·관측·네트워크 비용을 비교해야 한다.

## MSA와 서비스 분리

MSA(Microservices Architecture)는 업무 책임에 따라 서비스를 분리해 독립적으로 개발·배포·확장할 수 있도록 하는 접근이다. 클라이언트가 유사하다는 이유만으로 서비스를 분리하는 것이 아니라 **업무 경계와 데이터 책임**을 기준으로 설계한다.

서비스가 분리되어도 공통 진입점, 데이터베이스, 메시징 구성요소 등에 장애가 집중될 수 있다. 장애 격리는 서비스 경계뿐 아니라 이중화, 타임아웃, 재시도 정책, 장애 전파 차단 등을 함께 설계해야 달성된다.

## DDD와 Aggregate 할당

DDD(Domain-Driven Design)는 업무 도메인의 개념과 규칙을 중심으로 소프트웨어를 설계하는 접근이다.

- **도메인**: 해결하려는 업무 영역.
- **Bounded Context**: 특정 업무 모델과 용어가 일관되게 적용되는 경계.
- **Aggregate**: 함께 일관성을 유지해야 하는 객체와 규칙의 묶음.
- **Aggregate Root**: 애그리거트 외부에서 변경을 통제하는 대표 객체.
- **Aggregate 할당**: 애그리거트의 책임과 소유권을 어느 서비스에 둘지 결정하는 설계 활동.

애그리거트는 단순한 테이블 묶음이 아니며, 애그리거트 하나가 마이크로서비스 하나와 반드시 일대일로 대응하는 것도 아니다.

## Saga 패턴

Saga는 여러 서비스에 걸친 업무를 각각의 **로컬 트랜잭션**으로 처리하고, 중간 실패 시 별도 **보상 트랜잭션**으로 이전 작업의 효과를 취소·상쇄하도록 설계하는 패턴이다.

- **Choreography(안무형)**: 서비스가 이벤트를 주고받으며 다음 단계를 수행한다.
- **Orchestration(중앙 조정형)**: 조정자가 전체 실행·보상 순서를 관리한다.

Saga의 보상은 데이터베이스의 단일 트랜잭션 ROLLBACK과 같지 않다. 보상 실패, 중복 실행, 일시적 데이터 불일치에 대한 별도 처리가 필요하다. 모든 MSA에 Saga가 필수인 것은 아니다.

## DDD 기반 MSA 설계의 시각화

'시각화'는 도메인 경계, 애그리거트, 서비스 책임, API·이벤트 관계 등을 **다이어그램이나 모델링 도구로 표현한다**는 뜻일 수 있다. 표현 방식은 다음과 같이 구분된다.

| 방식 | 결과물 |
| --- | --- |
| 설계서 중심 | 문서·이미지·다이어그램 |
| 모델링 도구 중심 | 수정 가능한 도메인·서비스 모델 |
| 전용 조회 프로그램 | 별도로 개발한 웹·데스크톱 화면 |
| 운영 시각화 | 실제 서비스 호출·장애 상태를 표시하는 대시보드 |

'DDD 설계를 시각적으로 제공한다'는 문구만으로 별도 프로그램의 개발·납품을 뜻하지는 않는다. 납품물의 형식, 원본 모델의 편집 가능 여부, 라이선스, 갱신 책임을 명시해야 한다.


## 논리 계층과 물리 배치의 구별

아키텍처 다이어그램의 'Layer'는 기능적 책임의 분류일 수도 있고 실제로 분리 배포된 실행 단위일 수도 있다. 따라서 Frontend, Gateway, BFF, Backend라는 상자가 네 개 있다고 해서 서버 네 대가 존재한다는 뜻은 아니다. 하나의 웹 서버가 정적 파일 제공과 프록시를 겸할 수 있고, 하나의 애플리케이션이 여러 논리 계층을 포함할 수도 있다.

설계를 검토할 때는 **논리 구성도**(책임과 의존성), **배포 구성도**(프로세스·인스턴스·네트워크), **요청 흐름도**(실제 호출 경로)를 구별해야 한다. 같은 그림을 서로 다른 의미로 읽으면 불필요한 계층이 추가된 것처럼 보이거나, 실제 운영해야 할 구성요소가 누락될 수 있다.

## Gateway와 BFF의 책임 경계

Gateway와 BFF 모두 요청을 중계할 수 있지만 주된 관심사가 다르다. Gateway는 여러 API에 공통으로 적용할 정책과 경로 제어를 담당하고, BFF는 특정 클라이언트의 화면에 필요한 응답을 구성한다. 두 계층의 기능이 일부 겹친다는 이유만으로 둘 다 필수라고 볼 수 없다.

| 판단 질문 | 우선 검토할 책임 |
| --- | --- |
| 요청을 어느 서비스로 보낼 것인가? | Gateway 또는 기존 리버스 프록시 |
| API 호출량을 제한할 것인가? | Gateway의 공통 정책 |
| 한 화면에 필요한 여러 응답을 합칠 것인가? | BFF 또는 기존 애플리케이션 계층 |
| 화면마다 응답 필드와 형식이 다른가? | BFF 도입의 근거가 될 수 있음 |
| 업무 규칙과 데이터 변경은 누가 책임지는가? | 도메인 서비스와 애그리거트 |

BFF가 백엔드 API 여러 개를 대신 호출하면 **클라이언트에서 관측되는 요청 수**는 줄 수 있지만, BFF와 백엔드 사이의 호출까지 합친 **전체 네트워크 호출 수**는 오히려 늘 수 있다. 성능 개선 여부는 요청 수뿐 아니라 지연 시간, 병렬 호출, 캐시 적중률, 실패율로 판단해야 한다.

## 모놀리스에서 MSA로: 분리의 이익과 비용

단일 애플리케이션 내부에서도 Controller가 여러 Service를 호출하고 하나의 트랜잭션으로 데이터를 변경할 수 있다. 이런 구조는 서비스 사이의 통신이 주로 프로세스 내부에서 이루어지므로 호출 경로가 비교적 단순하다.

MSA로 나누면 독립 배포와 선택적 확장이 가능해질 수 있지만, 기존 메서드 호출이 원격 API 호출로 바뀌고 장애·지연·데이터 일관성 문제가 새롭게 발생한다. **서비스를 많이 나누는 것 자체는 품질 목표가 아니다.** 함께 변경되는 기능을 지나치게 분리하면 변경 한 건이 여러 서비스의 동시 배포를 요구할 수 있다.

클라우드 이전의 선택지도 단일하지 않다. 기존 구조를 유지한 이전, 실행 환경만 바꾸는 전환, 일부 업무만 점진적으로 분리하는 방식, 전체 서비스를 재설계하는 방식은 서로 다른 범위의 작업이다. 기술 선택은 독립 배포 필요성, 업무 경계의 안정성, 운영 역량을 근거로 해야 한다.

## 장애 지점과 장애 전파는 다르다

**단일 장애점(SPOF)**은 하나의 구성요소가 고장 나면 전체 기능이 중단되는 지점을 말한다. 반면 **장애 전파**는 한 서비스의 지연이나 오류가 다른 서비스로 퍼지는 현상이다. 서비스를 분리해도 공통 Gateway나 공유 데이터 저장소가 단일 장애점으로 남을 수 있고, 다중화만으로 원격 호출의 연쇄 지연이 사라지는 것도 아니다.

따라서 고가용성 설계에는 구성요소의 중복 배치와 더불어 호출 타임아웃, 제한된 재시도, 장애 차단, 대체 응답, 모니터링 등이 필요하다. 특히 재시도를 무제한 수행하면 장애 서비스에 요청이 집중되어 상황을 악화시킬 수 있다. 장애 격리는 'MSA 사용 여부'가 아니라 **고장 상황에서 어느 범위까지 영향이 퍼지는지**로 검증한다.

## 데이터 소유권과 분산 트랜잭션의 경계

애그리거트는 일관성을 유지할 경계를 제시하고, 서비스 경계는 배포와 데이터 책임을 구분한다. 서로 다른 서비스가 같은 테이블을 직접 수정한다면 서비스별 책임이 불분명해질 수 있다. 반대로 서비스마다 데이터를 나누면 기존의 단일 DB 트랜잭션으로 모든 업무를 원자적으로 처리하기 어려워질 수 있다.

이때 Saga는 선택지 중 하나다. 보상 작업은 이미 수행된 행위의 효과를 상쇄하는 **새로운 업무 처리**이며, 단순한 SQL ROLLBACK과 동일하지 않다. 따라서 보상 가능성, 중복 요청 처리, 실패 상태 기록, 운영자의 복구 절차를 함께 설계해야 한다. 모든 작업을 Saga로 연결하기보다 먼저 하나의 일관성 경계 안에서 처리할 수 있는지 검토하는 편이 중요하다.

## 설계 시각화 산출물의 검증

DDD 기반 설계를 시각화했다는 주장은 그림의 존재만으로 충분하지 않다. 도메인 경계가 어떤 근거로 도출되었는지, 애그리거트와 서비스의 소유권이 어떻게 대응하는지, 변경과 장애 시나리오가 설계에 반영되었는지 확인할 수 있어야 한다.

검토 가능한 산출물은 최소한 다음 질문에 답할 수 있어야 한다.

- 도메인·Bounded Context·애그리거트·서비스 사이의 관계를 추적할 수 있는가?
- 서비스 간 동기 호출과 비동기 이벤트를 구분했는가?
- 각 데이터의 수정 권한과 트랜잭션 경계가 명확한가?
- 논리적 계층과 실제 배포 단위를 혼동하지 않았는가?
- 모델 원본을 수정할 수 있으며 변경 이력을 관리할 수 있는가?

설계도와 운영 대시보드는 목적이 다르다. 전자는 **의도한 책임과 구조**를 보여주고, 후자는 **실제로 실행되는 호출과 상태**를 관측한다. 어느 하나가 다른 하나를 자동으로 대체하지는 않는다.

## 아키텍처 검토 기준

클라우드 이전에서 핵심 질문은 '새 계층을 도입하는가'보다 **기존 구조의 어떤 문제를 해결하는가**이다. Gateway는 API 관리 필요성, BFF는 클라이언트별 응답 차이, MSA는 업무별 독립성, DDD는 모델과 책임 경계, Saga는 분산 트랜잭션 문제를 각각 다룬다. 고가용성과 비용 절감은 별도 설계와 측정으로 검증해야 한다.
